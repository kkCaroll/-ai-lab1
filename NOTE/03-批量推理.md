# 批量推理

本篇说明自回归模型如何生成文本、为什么评测必须批量跑、以及批量引入的三个坑。相关代码为 `exp1/src/eval.py` 的批量生成函数。

## 一 自回归生成在做什么

语言模型只做一件事，给定一段 token 序列，输出下一个 token 在词表上的概率分布。生成时取分布中概率最大的那个 token 接到序列末尾，再算一次，循环往复，直到模型输出结束标记 `<|im_end|>` 或达到长度上限。

这里有一条不直观但很关键的性质。一次前向计算实际上同时算出了每一个位置各自的下一个 token 分布，而不只是最后一个位置的，因为注意力机制让每个位置都能看到它前面的全部内容。生成时只用最后一个位置的结果，其余算完即弃。但这条性质带来一个重要后果，同一批中不同序列共享同一次权重读取，批量的边际成本远低于线性增长。这是批量推理性价比极高的根本原因，也是本实验必须自己实现批量生成的原因。

P0 实测单条生成 17.6 token/s，对 0.6B 的模型而言这个数值偏低，低的原因正在于单条推理时 GPU 大部分时间在等待计算核的启动，而非在计算。GSM8K 测试集 1319 条按平均 200 token 估算共约 26 万 token，按单条速度需要四个多小时，批量之后预计在十五至三十分钟。DLC 按分钟计费，这一差别直接体现为账单。

## 二 填充方向

一批中各条题目的长度不同，要拼成矩阵必须补齐到同长。补在哪一侧有讲究。

自回归模型预测下一个 token 时靠的是序列的最后一个位置。若补在右侧，最后位置就成了填充符，模型会从填充符之后继续写，输出必然错乱。因此必须补在左侧，让最后位置永远是真实题目的结尾。

一个容易忽略的细节是分词器的填充方向有默认值。实测本机 Qwen3-0.6B 分词器的 `padding_side` 默认为 `right`，即错误的那一侧，必须显式改为 `left`，且必须在任何一次分词调用之前改。

## 三 注意力掩码

补在左侧之后，前面那段填充符不是有效内容，模型不该关注它们。但模型自己不知道哪些位置是补的，必须由外部显式告知。这个信息通过注意力掩码传入，它是一串与输入等长的 0 与 1，指明每个位置是否为真实内容。

掩码必须与输入一并送入模型。漏传的后果是填充符参与注意力计算，模型的注意力权重被分摊到无意义的位置上，输出质量下降。这类错误不会报错，只会让读数悄悄变低，属于最难发现的一类问题。

## 四 位置编码

模型靠位置编号理解 token 的先后顺序。左填充之后，真实内容的第一个 token 不在第 0 位，而在补齐段之后。若位置编号仍从 0 起算，真实内容的位置整体偏移，等价于把整道题往后挪了一段。

标准做法是由注意力掩码逐位累减算出真实位置再显式传入。做法是先对掩码沿序列维做累积和再减一，得到每个位置前面有多少个有效 token，再把无效位置填为 1。

## 五 KV 缓存与显存

生成过程中每一步都要重新计算注意力，但前面已经算过的键与值不必重算。缓存这批中间结果的张量就是 KV 缓存，它的体积由模型的注意力结构决定。

本机权重 `config.json` 给出的结构为 28 层、16 个查询头、8 个键值头、每头维度 128。缓存体积按下列方式估算。

```text
每条序列每 token 的缓存
  = 2（键与值）× 8（键值头数）× 128（每头维度）× 2（字节，float16）× 28（层）
  = 114688 字节
  ≈ 112 KiB
```

按下表估算一批数据的缓存体积，不含模型权重、激活值与 CUDA 运行时开销。

| 批大小 | 序列长度 512 | 768 | 1024 |
| --- | --- | --- | --- |
| 32 | 1.75 GiB | 2.63 GiB | 3.50 GiB |
| 64 | 3.50 GiB | 5.25 GiB | 7.00 GiB |

float16 下模型权重约 1.15 GiB，CUDA 上下文与算子工作区约 1.0 至 1.3 GiB。V100 可用显存 15.8 GiB，故批 32 配 768 序列总计约 5.1 GiB，批 64 配同长度约 7.7 GiB，两者均有充裕余量。

注意键值头数为 8 而查询头数为 16，这是分组查询注意力。键与值在多个查询头之间共享，使缓存体积降到不分组的二分之一。这个结构是现代小模型能在长上下文下保持显存可控的主要原因之一。

## 六 如何确认没有写错

上面三处任一写错，表现都是输出质量下降或整体错位，程序不报错。有一条最直接的检查能同时覆盖三者。

同一条样本单独跑一次，再放进一批里跑一次。贪心解码下两次的输出文本必须完全相同。若不同，说明填充方向、注意力掩码或位置编码至少有一处写错。

这条检查在本机以处理器运行只需几分钟，是拦截这类错误最划算的手段，计划中列为 P1.4 的验收条件之一。

## 七 可以自己验证的两点

打印左填充后一批的输入编号矩阵与掩码矩阵，确认填充位置在每行的开头而不是结尾，且掩码在对应位置为 0。本机实测的结果是短序列行形如 151643 重复若干次后接真实编号，掩码相应为若干个 0 后接 1。

把批大小从 1 逐步增大，记录每一步的平均耗时。若每步耗时随批大小增长得远比线性慢，说明 GPU 的空闲正在被填满，这可以直观说明批量为什么划算。
