# 实验一 代码结构

本节于 2026-10-12 定为定稿，据此建立仓库目录。文中标注「提案期约定」的条目为 2026-10-11 起草、实施时收敛后的结果，收敛理由一并记录。

## 二 脚本接口

统一入口，方法差异全部由参数控制，不为每种方法单独修改文件内容。

训练入口，P2 建立

```bash
python -m src.train --config configs/<method>.yaml \
                    --data-dir <挂载路径> \
                    --output-dir <运行目录> \
                    [--set 键路径=值 ...] \
                    [--seed 42]
```

提案期的训练入口含 `--method {sft|lora|ptuning|custom}` 与 `--config` 两项，实施时收敛为只留 `--config`，方法名改由配置文件内的 `method` 键给出。理由与评测入口的 `--output` 收敛同理，两处各记一份方法名即构成两处真源，不一致时还会静默取其一。`--set` 为可重复的键值覆盖，供 P2.5 扫参与本机自检使用，见下。

配置分三层，后者覆盖前者，逐段深合并而非整段替换。第一层 `configs/base.yaml` 记五种方法共用的默认值。第二层 `configs/<method>.yaml` 记方法专属超参，段名与方法名同名，方法与模块的对应关系即 `full_sft` 对 `src/methods/sft.py`，其余三者同名。第三层为命令行 `--set`，优先级最高。键的存放规则一句话，凡描述训练本身的进配置文件，凡随调用而变的进命令行，据此模型路径、数据目录、输出目录与运行标识四项不写入任何一层，理由是同一份配置要在本机与容器两处生效而两处路径不同。镜像与实例规格、最长运行时长、任务名三项属平台侧，不进配置文件，提交任务时填写并记入 `RECORD/02-环境信息.md`。

基座段 `run` `data` `train` `eval` `output` 的键空间由 `base.yaml` 声明，方法段的键空间由其对应模块声明，`--set` 指到未被声明过的键路径时判 FAIL 并中止。拼错一个键而静默无效，会使扫参得出的结论成为错的，故此处不作宽容。

`--set` 的值按字面推断类型，`16` 为整数、`2.0e-4` 为浮点、`true` 为布尔、其余为字符串。配置内的浮点一律写成 `1.0e-4` 的形式，YAML 1.1 只把含小数点的尾数认作浮点，写成 `1e-4` 会被读成字符串。

训练运行的输出目录下另落一份 `config.json`，除照录三层合并后的配置外，记四个派生量，即 `prompt_version`、`prompt_sha256`、`train_size` 与 `effective_batch_size`。前两项与评测入口已落盘的 `config_<dataset>.json` 同名同义，故 R8 的证据由人工打印比对升级为两个文件间的一次等值检查。

中间评测的 `eval.dataset` 只接受 `dev`，取值校验写在配置解析处而非训练循环内，使写错在启动时即报错。该限制对应 R7，训练过程中的任何评测都不得触及测试集。

为此于 2026-10-13 对 `src/eval.py` 作一次最小改动，把生成与抽取两步自 `evaluate_dataset` 抽为 `predict_examples(model, tokenizer, encoded, examples, dataset, device, batch_size, max_new_tokens)`，返回逐条记录与生成统计，不写产物也不打印汇总。`evaluate_dataset` 改为调用它，对外行为与五类产物不变。训练侧调用同一函数，故训练中的开发集读数与独立评测出自同一条代码路径，两者可比是结构保证而非约定。抽取时另在函数内把模型切至推理态并暂开缓存开关，用毕还原，否则训练态下 dropout 会随手生效而使贪心解码失去确定性。批量生成的实现即 `_make_batch` 与 `_generate` 两处一字未动，P1 已自检过的左填充与位置编号不受本次改动影响。

`src/config.py` 于同日建立，承担配置的加载、三层合并与校验。它只依赖 PyYAML，不导入 torch，故 `tests/test_config.py` 能像抽取模块的测试一样以毫秒级跑完。方法段的键空间不在该模块内，因为方法模块在导入期即依赖 peft 与 torch，故加载分两步，`load` 负责两层文件与命令行覆盖，`apply_method` 由调用方在导入方法模块之后调用，补上方法段的校验与默认填充。

`src/methods/` 下四个模块的契约见该包 `__init__` 的模块说明，要点是每模块暴露 `METHOD`、`CONFIG_SCHEMA` 与 `build`、`describe`、`extra_loss`、`save` 四个函数，签名与语义完全一致。`config` 只传本方法自己那一段，方法模块看不到 `train` 与 `data` 两段，也无从读到数据集路径，R6 的约束由接口结构保证而非靠自觉。用函数而不用类，与 `src` 下其余模块的写法一致。`extra_loss` 现在就立，三个方法的实现都是返回空，使 P3 不必回头改动训练入口。

M3 的实现挂在 peft 的 `PrefixTuningConfig` 而非名为 P-Tuning 的 `PromptEncoderConfig` 上。两者在 peft 中的命名容易混淆，故在一份四层的微型 Qwen3 上实测确认，`PromptEncoderConfig` 的输出仍拼在输入嵌入之前，前向序列长度随虚拟 token 数等量增加，属 P-Tuning；`PrefixTuningConfig` 不改输入长度，改在每一层的注意力缓存里多出与虚拟 token 等长的键值对，属 P-Tuning v2。理由与证据见 `src/methods/ptuning.py` 的模块说明与 `LOG/02-问题与解决.md` 的 Q10。

`train.py` 另有一处不能忘的调用。开启梯度检查点而又冻结词嵌入时，输入不参与计算图，梯度回传不到适配器，损失会一动不动而任务照常跑完。解法是装配后调一次 `enable_input_require_grads`，全参微调下该调用无害。此属通用处置，放在训练入口的模型准备处，不进方法模块。

评测入口

```bash
python -m src.eval --model-path <路径> \
                   --adapter <路径或留空> \
                   --dataset {gsm8k|arc} \
                   --data-dir <挂载路径> \
                   --split {test|dev} \
                   --output-dir <运行目录>
```

提案期的评测入口为 `--output <结果文件>`，实施时收敛为 `--output-dir <运行目录>`，理由是评测一次要同时产出逐条明细、汇总指标、配置快照与环境快照四类内容，落成目录与第三节的输出约定一致。

P1.4 实现时在提案的参数之外补齐四项。`--dataset` 接受逗号分隔的多个数据集，两者在一次调用内串行完成并共用一份已加载的模型，省去一次加载。`--batch-size` 与 `--max-new-tokens` 的留空值按数据集取默认，GSM8K 为 32 与 512，ARC 为 64 与 128，同一数据集内各方法共用同值，故 R13 不受影响。`--limit` 供本机小样本自检，置位时跳过与期望行数的核对。`--check-consistency` 取前若干条比较单条与批量生成的输出，用以拦截左填充、注意力掩码与位置编号三类写错，本机自检时置为不小于 2，容器全量运行时不启用。

容器内的调用由 `scripts/run_eval.sh` 承载，模型路径、数据目录与输出目录三项经环境变量注入，适配器为可选项，故同一脚本可供 M0 至 M4 各方法复用，不必为每种方法改文件内容。

P1.6 期间另补 `scripts/reextract.py`，用于抽取规则迭代后按当前规则重算既有运行目录。逐条明细中的 output 字段是模型原样输出，与抽取规则无关，故可据其在本机离线重算 pred、判定与指标，既不重跑模型也不占用 DLC 计量时长。该脚本只改动抽取相关字段，生成耗时与显存峰值等取自原指标文件；重算前逐条比对取值，原先判对的样本若出现取值改动即判 FAIL 并中止，使规则改动在既有正确结果上引入的回归无处隐藏。脚本一次运行一份运行目录，签名与评测入口同源的字段命名一致，便于日后由 `RECORD/` 回溯。

两个入口均以 `python -m` 方式调用，工作目录设于 `exp1/`，使 `src` 作为包被导入。容器内的形式为 `cd /mnt/code/AI_lab1/exp1 && python -m src.eval ...`。

被评测的方法与训练超参通过配置文件传递，训练与评测共用 `src/data.py` 中的模板函数，以保证 R8 得到控制。模板文本只存在于该模块，配置文件只引用 `PROMPT_VERSION`，不复写文本。

## 三 输出约定

每次运行在输出目录下生成一份运行记录，供 `RECORD/01-实验配置.md` 直接誊录。

| 文件 | 内容 |
| --- | --- |
| `config_<dataset>.json` | 本次运行的全部超参与解码配置快照 |
| `env.json` | 库版本、GPU 型号、显存峰值 |
| `metrics_<dataset>.json` | 准确率、抽取失败率、截断率、各抽取规则命中计数与耗时 |
| `predictions_<dataset>.jsonl` | 逐条预测与抽取结果，供人工抽查 |
| `extract_failures_<dataset>.jsonl` | 抽取失败与降级的样本，供现象记录引用 |
| `train.log` | 训练日志，P2 起产生 |

输出目录以运行标识命名，不复用旧目录，以规避 OSS 不支持覆盖写的问题。产物在内存聚合后一次写出，任务中途失败即换新标识重跑，不在同一目录续写。

评测的 prompt 全文不落盘，只落其 sha256，用于核对训练与评测共用同一模板，同时控制体积。

## 四 已知的代码重复

`src/utils.py` 与 `scripts/smoke_dlc.py` 各含一份报告机制，即 `OK` `WARN` `FAIL` 三常量与 `Check` 数据结构及配套函数。

此重复为有意保留。`scripts/` 下的脚本须在 `src` 不在 `sys.path` 时仍能独立运行，P0 期间确曾以脚本单文件方式提交容器任务，若改为导入 `src` 则须同时调整提交命令与既有产物引用。`scripts/smoke_dlc.py` 的输出已在 `RECORD/02-环境信息.md` 第四节被引用，不宜在 P1 期间改动。

后续若 `scripts/` 不再需要独立运行，可将两者合并，届时一并更新本节。

`scripts/prepare_data.py` 另含一份 `sha256_of`，与 `src/utils.py` 的同名函数重复，理由同上，且该脚本的产物 `data/raw/manifest.json` 已被 `RECORD/02-环境信息.md` 第三节引用，P1 期间不改。

于 P1.5 新增的 `scripts/make_dev_split.py` 不沿用上述做法，改为导入 `src/utils.py`。理由是该脚本只在本机运行一次，产物 `exp1/configs/dev_split.json` 入仓库后由 `src/data.py` 消费，容器内不执行本脚本，因而不存在独立运行的需要，再写一份 `sha256_of` 与报告机制没有收益。调用形式相应改为在 `exp1/` 目录下执行 `python -m scripts.make_dev_split`，使 `src` 与 `scripts` 同时可导入。
