# 实验一 代码结构

本节于 2026-10-12 定为定稿，据此建立仓库目录。文中标注「提案期约定」的条目为 2026-10-11 起草、实施时收敛后的结果，收敛理由一并记录。

## 一 目录布局

仓库根目录即当前实验文件夹，代码置于 `exp1/` 之下，与 `PLAN/`、`RECORD/`、`LOG/`、`NOTE/`、`DLC使用文档/` 平级。`scripts/` 存放跑一次即完成的实验脚本，`src/` 存放会被反复调用的库代码，后者在 P1 起建立。


## 二 脚本接口

统一入口，方法差异全部由参数控制，不为每种方法单独修改文件内容。

训练入口，P2 建立

```bash
python -m src.train --method {sft|lora|ptuning|custom} \
                    --config configs/<method>.yaml \
                    --data_dir <挂载路径> \
                    --output_dir <输出路径> \
                    --seed 42
```

评测入口

```bash
python -m src.eval --model-path <路径> \
                   --adapter <路径或留空> \
                   --dataset {gsm8k|arc} \
                   --data-dir <挂载路径> \
                   --split {test|dev} \
                   --output-dir <运行目录>
```

提案期的评测入口为 `--output <结果文件>`，实施时收敛为 `--output-dir <运行目录>`，理由是评测一次要同时产出逐条明细、汇总指标、配置快照与环境快照四类内容，落成目录与第三节的输出约定一致。

P1.4 实现时在提案的参数之外补齐四项。`--dataset` 接受逗号分隔的多个数据集，两者在一次调用内串行完成并共用一份已加载的模型，省去一次加载。`--batch-size` 与 `--max-new-tokens` 的留空值按数据集取默认，GSM8K 为 32 与 512，ARC 为 64 与 128，同一数据集内各方法共用同值，故 R13 不受影响。`--limit` 供本机小样本自检，置位时跳过与期望行数的核对。`--check-consistency` 取前若干条比较单条与批量生成的输出，用以拦截左填充、注意力掩码与位置编号三类写错，本机自检时置为不小于 2，容器全量运行时不启用。

容器内的调用由 `scripts/run_eval.sh` 承载，模型路径、数据目录与输出目录三项经环境变量注入，适配器为可选项，故同一脚本可供 M0 至 M4 各方法复用，不必为每种方法改文件内容。

P1.6 期间另补 `scripts/reextract.py`，用于抽取规则迭代后按当前规则重算既有运行目录。逐条明细中的 output 字段是模型原样输出，与抽取规则无关，故可据其在本机离线重算 pred、判定与指标，既不重跑模型也不占用 DLC 计量时长。该脚本只改动抽取相关字段，生成耗时与显存峰值等取自原指标文件；重算前逐条比对取值，原先判对的样本若出现取值改动即判 FAIL 并中止，使规则改动在既有正确结果上引入的回归无处隐藏。脚本一次运行一份运行目录，签名与评测入口同源的字段命名一致，便于日后由 `RECORD/` 回溯。

两个入口均以 `python -m` 方式调用，工作目录设于 `exp1/`，使 `src` 作为包被导入。容器内的形式为 `cd /mnt/code/AI_lab1/exp1 && python -m src.eval ...`。

被评测的方法与训练超参通过配置文件传递，训练与评测共用 `src/data.py` 中的模板函数，以保证 R8 得到控制。模板文本只存在于该模块，配置文件只引用 `PROMPT_VERSION`，不复写文本。

## 三 输出约定

每次运行在输出目录下生成一份运行记录，供 `RECORD/01-实验配置.md` 直接誊录。

| 文件 | 内容 |
| --- | --- |
| `config_<dataset>.json` | 本次运行的全部超参与解码配置快照 |
| `env.json` | 库版本、GPU 型号、显存峰值 |
| `metrics_<dataset>.json` | 准确率、抽取失败率、截断率、各抽取规则命中计数与耗时 |
| `predictions_<dataset>.jsonl` | 逐条预测与抽取结果，供人工抽查 |
| `extract_failures_<dataset>.jsonl` | 抽取失败与降级的样本，供现象记录引用 |
| `train.log` | 训练日志，P2 起产生 |

输出目录以运行标识命名，不复用旧目录，以规避 OSS 不支持覆盖写的问题。产物在内存聚合后一次写出，任务中途失败即换新标识重跑，不在同一目录续写。

评测的 prompt 全文不落盘，只落其 sha256，用于核对训练与评测共用同一模板，同时控制体积。

## 四 已知的代码重复

`src/utils.py` 与 `scripts/smoke_dlc.py` 各含一份报告机制，即 `OK` `WARN` `FAIL` 三常量与 `Check` 数据结构及配套函数。

此重复为有意保留。`scripts/` 下的脚本须在 `src` 不在 `sys.path` 时仍能独立运行，P0 期间确曾以脚本单文件方式提交容器任务，若改为导入 `src` 则须同时调整提交命令与既有产物引用。`scripts/smoke_dlc.py` 的输出已在 `RECORD/02-环境信息.md` 第四节被引用，不宜在 P1 期间改动。

后续若 `scripts/` 不再需要独立运行，可将两者合并，届时一并更新本节。

`scripts/prepare_data.py` 另含一份 `sha256_of`，与 `src/utils.py` 的同名函数重复，理由同上，且该脚本的产物 `data/raw/manifest.json` 已被 `RECORD/02-环境信息.md` 第三节引用，P1 期间不改。

于 P1.5 新增的 `scripts/make_dev_split.py` 不沿用上述做法，改为导入 `src/utils.py`。理由是该脚本只在本机运行一次，产物 `exp1/configs/dev_split.json` 入仓库后由 `src/data.py` 消费，容器内不执行本脚本，因而不存在独立运行的需要，再写一份 `sha256_of` 与报告机制没有收益。调用形式相应改为在 `exp1/` 目录下执行 `python -m scripts.make_dev_split`，使 `src` 与 `scripts` 同时可导入。
